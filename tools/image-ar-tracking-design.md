# 浏览器端图像 AR 跟踪 · 设计与实现方案

> 目标：在**网页**里做到"对准卡片 → 稳稳跟住 → 鱼不抖不掉"。
> 现在的 pattern（AR.js）能用但抖、纯二维码原型（qr-prototype）思路错在跳过跟踪阶段，
> 本文给出可实现的正确管线。

## 1. 现状与问题

| 方案 | 检测 | 跟踪 | 位姿 | 结果 |
|---|---|---|---|---|
| AR.js pattern（线上主页） | 每帧黑框四边形检测 | **无** | 单应/模板 | 能用，但每帧独立 → 世界坐标一跳一跳 |
| 纯二维码原型（qr-prototype） | 每帧 QR 解码 | **无** | 四点 PnP | 解码失败即丢，10Hz 台阶感 |
| 系统级（ARCore/ARKit/xr-frame） | 离线特征库 | **有（含 IMU 融合）** | 系统级 | 稳 |

**结论：差距不在"检测算法好不好"，而在缺了"跟踪"这一整段。**

## 2. 管线设计（与线上实现一致，2026-09-21 校准）

```
相机 640×480 → 灰度化
  │
  ├─【首次捕获】半分辨率全图 ORB 定位 → 立刻用它的四角开 ROI、全分辨率重检（"粗→精"）
  │
  ├─【重检测】以下任一成立时：每 30 帧 / 内点 < 0.75×阈值 / 上一帧没算出位姿
  │     ROI（有历史位姿时）或全图 ORB + BFMatcher(ratio 0.75) + RANSAC(3px)
  │       → 内点 ≥ 20 且过"三层位姿质检"才算成功 → 重新布 8² 网格
  │
  ├─【跟踪态】每帧：ROI 内 KLT(21×21, 金字塔 3 层)
  │       → findHomography(RANSAC 3px) → 三层位姿质检
  │       → solvePnP(IPPE_SQUARE) + solvePnPRefineLM
  │       → One-Euro（只滤平移，dt 用实测帧间隔）→ 写锚点矩阵
  │
  └─【丢失判定】连续 2 帧没位姿才发 markerLost（短暂丢失不隐藏鱼，避免闪）；
                 重新锁定时跳过"尺寸突变"检查（卡片本来就可能远近不同）
```

### 2.1 检测（Detection）
- 特征：**ORB(1000)** 多尺度参考（卡片画布 480 宽 → 参考尺度 480/240/154/106）。AKAZE 只写在方案里，**未实现**
- 匹配：BFMatcher(Hamming) + Lowe ratio 0.75；首次捕获用全部尺度，ROI 重检只用最接近当前卡片大小的 2 个尺度
- 几何：`findHomography(RANSAC, 3px)`，内点 ≥ 20
- **粗→精**：首次捕获那遍半分辨率只用来定位（实测它会给小卡片 25px 偏差 + 10° 假旋转），随后 ROI 全分辨率重检再交出去
- 粗检固定半分辨率，**不随自适应档位缩放**（否则档位降到 0.6 时卡片只剩几十像素，重新捕获会失败）

### 2.2 跟踪（Tracking）
- KLT：`calcOpticalFlowPyrLK`，winSize 21×21，金字塔 3 层
- 布点：卡片 0.1~0.9 区域**均匀网格 8²**（自适应最低 5²）——比随机角点抗漂移
- 单应重算：跟踪点 ↔ 卡片规范坐标 → RANSAC 3px。**阈值不随处理分辨率缩放**（实测收紧只会更容易丢：1.8px 阈值出位姿 43/70 vs 3.0px 54/70）
- ROI：卡片外扩 0.9 倍（跟踪）/ 0.3 倍（检测）；ROI 里没找到时立刻回退半分辨率全图重检

### 2.3 位姿与"三层质检"
- `solvePnP(objPts4, imgPts4, K, dist, rvec, tvec, false, SOLVEPNP_IPPE_SQUARE)` + `solvePnPRefineLM`
- 内参：`f = (W/2)/tan(hfov/2)`，hfov 60°，主点=画面中心；卡片宽度 = 1 世界单位
- 三层质检（顺序执行，任一不过就当"本帧没锁住"）：
  1. **几何合理性**：有限值 / 凸且不自交 / 面积在画面面积的 0.13%~800% / 边长比 ≤ 8
  2. **内点数**：跟踪帧 ≥ max(10, 0.3×点数)，检测帧 ≥ 20
  3. **帧间尺寸突变**：相邻帧卡片尺寸比必须落在 0.7~1.4（噪声下曾出现连续 100 帧"深度减半"的假锁定）
- `solvePnP` / `RefineLM` 抛异常时只记日志并按丢失处理，绝不让异常打断 rAF 循环

### 2.4 滤波与自适应档位
- **One-Euro 只作用在平移**（x/y/z 共用一组参数），旋转直接用 solvePnP 输出
- 线上参数：`mincutoff 0.2 / beta 0.05 / dCutoff 1.0`（扫参：同样 +0 帧延迟下，比 0.2/0.2 的抖动降幅 71% → 88%）
- `dt` 用**实测帧间隔**（EMA，夹在 4~200ms），不写死 1/30——否则帧率在 30/60fps 间变化时时间常数会跟着漂
- **自适应档位由实测帧间隔驱动**：>33ms 降档、<25ms 且成本富余才升档；档位 = 处理分辨率 1.0→0.45 × 跟踪点 8²→5²
  （原来只看"跟踪+摊薄检测"的成本估值，漏掉渲染开销：节流 ×4 时跟踪报 19ms、真实帧间隔 42ms）
- 未实现（诊断结论是不需要）：IMU 帧间预测、预测渲染 0.5 帧——面板会报"位姿率 vs 渲染帧率"，需要时再加

## 4. 性能预算与实际值（实测见 §11，处理分辨率 640×480）

| 阶段 | 设计预算 | 实测（桌面 Chrome / 假摄像头） |
|---|---|---|
| KLT（8²=64 点） | 3~8 ms | **3.2 ms** |
| RANSAC 单应 | 1~3 ms | **4.8~7.7 ms**（比预算高，是当前跟踪帧的大头；试过用最小二乘替掉，精度崩 5~8 倍，见副本仓 results 第九/十/十二轮） |
| 位姿 + 滤波 | <1 ms | <1 ms |
| ORB ROI 重检测 | 15~40 ms | **39~48 ms**，每 30 帧一次（摊薄 ≈1.4ms/帧） |

→ 桌面浏览器稳态 50~60fps；CPU 节流 ×4（≈普通手机）时自适应降到 544×408/5²，**33.4fps**；
重检测那一帧会掉到 20fps 左右（每 30 帧一次，肉眼是轻微顿一下）。

## 5. 失败判定与状态机

```
LOST ──检测成功(内点≥20 且过三层质检)──▶ TRACKING
  ▲                                      │
  └──连续 2 帧没算出位姿─────────────────┘
     （触发条件：ROI 检测失败 / 内点 < 0.75×阈值 / 位姿没通过质检）
```
- 进入 LOST 后**先不隐藏鱼**：给 1~2 秒宽限（鱼继续按最后一次位姿游），仍失败才走退场动画
- 恢复时**不重置鱼的位置**（避免瞬移），沿用现有 `startEntering/startExiting` 语义

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| 水墨卡留白多、特征少 | 先跑**特征密度评估**；不足则卡面加淡纹/印章等纹理，或改用 ArUco 类黑方块 |
| OpenCV.js 体积 10.9MB | 首屏先用 pattern 兜底，加载完再切换跟踪器；或用精简构建 |
| iOS 陀螺仪权限 | 在用户手势（点击开始）里 `requestPermission()`，失败则退化为纯视觉 |
| 跟踪漂移（跟偏了） | 每 15~30 帧强制重检测 + 重投影误差阈值判据 |
| 手机性能差异 | 分辨率自适应（已有）+ 检测分帧摊开 |

## 8.5 部署与缓存（踩过的坑）

**OpenCV 走多源加载**（`js/opencv-loader.js`）：官方 CDN 在 Cloudflare 后面，实测会间歇性返回
403 挑战页（`Just a moment...`）——挑战页是 HTML，当 `<script>` 加载不会触发 onerror、只抛
SyntaxError，表现就是"相机出来了、一直没有鱼"。加载器按顺序试
`jsDelivr(@techstark/opencv-js 4.12)` → `docs.opencv.org`，每个源等 15 秒看 `window.cv` 有没有
就绪，没好就换下一个；跟踪器自己轮询 `window.cv`，所以只要有一个源成功就能起来。
（本机无外网，无法在无头浏览器里验证真 CDN 可达性，但单源与"首源失败→回退"两条路径都实测过；
另外把跟踪器用到的 OpenCV 调用在 jsDelivr 那份构建上逐个跑过：ORB / BFMatcher.knnMatch /
findHomography(RANSAC) / solvePnP(IPPE_SQUARE)+RefineLM / calcOpticalFlowPyrLK 全部正常，
只缺 `imreadMulti` 与 `createCLAHE`——线上都没用到。探针脚本：副本仓库 `opencv-api-probe.js`。）

`index.html` / `tracker-prototype/index.html` 里的脚本都带版本串（`?v=N`）。GitHub Pages 会给
JS 发缓存头，**改了 `js/image-tracker.js` 必须同时把这几个 `?v=` 加一**，否则手机拉到的还是旧算法
（页面 URL 上带 `?v=` 只能穿透 HTML 自己的缓存，挡不住脚本缓存）。卡片参考图走"换文件名"
（`pattern-card-v3-track.png`）而不是原地改，避免同一个坑。

## 10. 真机首次验证：卡在"正在打开相机…"的根因（2026-09-21）

手机首次打开 `tracker-prototype/` 时，画面停在"正在打开相机…"，调试行显示
`cv=ok | 卡片=0×0 | 参考=0层`。查下来是**两条各自独立的加载卡点**，都不是跟踪算法本身：

| 根因 | 证据 | 处理 |
|---|---|---|
| 卡片参考图 1.4MB / 2000×2000 | 同一网络下拉这个 PNG 实测 **50.4s**（校验和与本地一致，纯粹是慢）；跟踪器只用得上 480×480（`S.card` 固定画到 480 宽，参考尺度 1.0/0.5/0.32/0.22） | 新增 `assets/patterns/pattern-card-v2-track.png`（480×480，**71KB**）并改跟踪器默认引用；2000×2000 原图保留给 pattern 生成用 |
| 相机启动被 a-scene 的 `loaded` 事件挡住 | 该事件要等 `a-assets` 里两个 GLB（合计 2.1MB）下载完，慢网络下几十秒；期间 `startCamera()` 根本没被调用 | 相机改成 `window.load` 就启动；`tick()` 改为等"锚点已初始化"再跑跟踪。相机画面先出来，鱼等模型 |

附带一点：`solvePnP` / `solvePnPRefineLM` 在退化配置下会抛异常，未接住会打断整个
`requestAnimationFrame` 循环（画面永久卡死）。现在位姿先过 `quadRejectReason`
（有限性/凸性/面积/边长比），不通过就当"本帧没锁住"；真有异常也只记日志并让本帧按丢失处理。

退化压力测试的完整数据与"试过但没采用的手段"见副本仓库
`tracker-lab-results.md` 第九轮（含 `equalizeHist`、KLT 大窗口两组反例）。

**精度口径提醒**：上面的角点误差跟"参考图的尺度表有没有包住卡片当前大小"强相关。
同一序列只换参考图：1000px 参考（尺度 1000/500/320/220）2.29px、960px 参考 5.12px、
480px 参考 10.93px。浏览器用的是卡片画布 480（尺度 480/240/154/106，覆盖 110-280px），
正好落在上面这张表的可用范围里；曾试过把画布提到 960（尺度最小层 211px），
卡片只有 150px 时反而没有合适尺度，所以**不采用**。

周期重检测间隔取 30 帧（`tracker-lab-results.md` 第十二轮的扫参：干净场景越长越好、运动模糊
越短越好，30 是拐点；相对 45，模糊 13.61→7.99px、噪声 9.74→6.55px、变暗 7.12→5.63px，
干净场景只差 0.44px，检测摊薄 0.93→1.4ms/帧）。

首次捕获是"粗→精"两步：半分辨率全图只负责定位，拿到大致位置后立刻开 ROI 全分辨率重检一次。
改之前卡片只有 ~220px 宽时，粗检会给出带 10° 假旋转、偏 25px 的位姿（然后被当先验跟踪下去）；
改之后帧 0 的四角偏差 ≈1-2px，全程角点误差从 8.14px 降到 3.31px。粗检分辨率固定半分辨率，
不再乘自适应档位（否则档位降到 0.6 时 `ds=0.3`、卡片只剩几十像素，重新捕获会失败）。

**自适应档位怎么定的**：由**实测帧间隔**驱动——`frameMs > 33`（即掉出 30fps）就降档，
跟踪点 8²→5²、处理分辨率 1.0→0.45。原来只看"跟踪+摊薄检测"的成本估值，会漏掉渲染开销
（CPU 节流 ×4 时跟踪报 19ms、真实帧间隔 42ms，档位误以为还有富余）。下限取 0.45/5²：
再往下跟踪点只剩 4²（16 点）或分辨率 224×168（卡片只剩约 56px，参考图最小 106px 对不上）。

**现场光线**（真浏览器实测，见 `tracker-lab-results.md` 第十六轮）：运动模糊不虚（锁定率 93%），
但**变暗 0.55 掉到 70%、噪声 15 只有 48%**，且变暗时位姿是"稳定地偏"（误差 37→58px 平滑漂移），
时序保护救不了。结论：卡片要打光、别在昏暗场地硬拍；确实暗就优先走 AR.js pattern（黑方块对比度天然够）。
预处理试过 preblur 3×3/5×5、CLAHE clip 2/3，**全都得不偿失**，没有采用。

**位姿质检现在有三层**：①几何合理性（有限/凸/面积/边长比）②内点不足就丢 ③**帧间卡片尺寸突变**

同一份静止噪声输入下，跟踪器曾连续 100 帧锁在"深度减半"的错误位姿上（2× 尺度错），
